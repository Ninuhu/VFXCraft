# VFXCraft 保存・出力形式

版: 1.0 / 2026-11-03  
**拡張子と用途は確定。内部仕様は本書の設計案であり、未実装・未採用。** ADR-003/004/006を経て実際のスキーマに落とし込む。

## 1. 形式を混同しない

| 形式 | 確定した用途 | 編集データ・素材の扱い |
| --- | --- | --- |
| `.vcr` | 編集内容と素材を保存し、後から再編集 | プロジェクトを再構築できる情報を保持 |
| PNG連番 | 2Dアニメーションをフレーム単位で出力 | 描画結果。キーや階層の保存を代替しない |
| スプライトシート | 2Dアニメーションを1枚の画像へまとめる | 描画結果。シート付随メタ情報形式は未決 |
| 3D JSON | 3Dエフェクトの設定データを保存・出力 | JSONスキーマと素材参照方式は未決 |
| ブラウザ内自動保存 | 作業中の編集内容を復元 | `.vcr`の手動保存と並行して動作 |
| 自作プリセット | エフェクト構成を再利用・再編集 | ファイル拡張子・保存先・素材同梱規則は未決 |

3DデータをJSONで扱う決定は、`.vcr`自体を単一JSONに限定する決定ではない。ブラウザ内にSQLiteを採用することも未決。

## 2. `.vcr`内部構造の候補

Q10で提示された候補は以下。**ZIPベース案を採用済みと扱わない。**

```text
MagicExplosion.vcr
├── project.json
├── assets/
│   ├── fire.png
│   ├── smoke.webp
│   └── spark.png
└── metadata.json
```

比較する項目は、素材同梱、保存/読込時間、メモリ使用、壊れたファイルの検出、ブラウザ対応、将来の移行のしやすさ。ZIPか別方式かはADR-004で採用理由と検証結果を残す。

## 3. 論理的に保持すべき内容（設計案）

物理ファイル構成が変わっても、次の論理情報を保存契約にする。

| 論理情報 | 内容 |
| --- | --- |
| 識別 | VFXCraft専用の識別子、形式バージョン、作成アプリ版 |
| プロジェクト | ID、名前、2D/3Dモード、時間設定 |
| レイヤー | ID、階層、兄弟順序、表示、ロック、変換、開始時間 |
| エフェクト設定 | 連続/Burst、粒子設定、材質、描画方式、基本Bloom |
| アニメーション | 位置・回転・サイズ・色・透明度のトラック、キー、補間 |
| 素材 | 安定ID、形式、寸法、格納先、画像本体、任意の整合性情報 |
| 再現用情報 | 乱数シード等、採用した再現性設計に必要な値 |
| メタ情報 | 作成/更新情報等。必須・任意の範囲は別途決める |

外部URLにしかない素材や一時URLへ依存せず、別環境で再編集可能にする。内蔵素材の同梱/参照方式、画像の再圧縮の有無はADRで決める。

### 保存しないものの案

GPUリソース、デコード済みキャッシュ、実測FPS、実行中の全粒子、APIキー、言語・テーマといった利用者固有設定。現在の選択・カメラ等の保持範囲は、プロジェクト情報とプレビュー設定を分けたうえで決める。

## 4. 読込と互換性（設計案）

1. 拡張子だけで判定せず、専用識別子とバージョンを確認する。
2. ファイル全体の構造、サイズ上限、必須要素を検証する。
3. JSONの型、有限数、IDの一意性、親子の循環、キー対象、素材参照を検証する。
4. 対応する旧バージョンは明示的に移行し、再検証する。
5. 画像をデコードでき、必要な素材がそろっていることを確認する。
6. 成功した場合のみ編集中のドキュメントと置き換える。失敗時は現状を保持する。

未知の新バージョンを黙って旧形式として開かない。対応外機能を失った状態で上書きしない。ZIP方式を採る場合は、展開後容量、件数、階層、パスの検証も契約に含める。数値上限は測定後に定義する。

## 5. 自動保存・復元（設計案）

- 保存単位はプロジェクトと必要素材の整合性が保たれたスナップショット。
- 書込中断で直近の正常な復元データを失わない方式を選ぶ。
- ブラウザを閉じて再開するフローで復元を確認する。
- 復元候補と編集中の内容を区別し、意図せず置き換えない。
- 容量不足や保存失敗を表示し、手動の`.vcr`保存へ進める。
- ブラウザ側のデータ消去まで防げるとは説明しない。自動保存と持ち出せるプロジェクトファイルの役割をヘルプへ記載する。

未決: 自動保存間隔、保存世代数、複数プロジェクトの扱い、履歴の復元範囲。復元候補は日時を表示して利用者が選択する。これらをMVP-Bから自動保存を外す理由にしない。

## 6. 画像エクスポートの契約案

必須入力は解像度・FPS・透過・出力範囲。以下はADR-006で決める設計案。

- 出力範囲を秒またはフレームで入力し、内部で一意のフレーム時刻列へ変換する。
- 終端は半開区間`[start, end)`を第一候補とする。確定前に境界フレームの受け入れ例を作る。
- 整数の制作フレーム範囲`[0, 60)`を同じFPSで出力する場合、60画像となる例を基準にする。異なる出力FPSでの換算・丸めは別途定義する。
- PNG連番の番号規則と配布方法、シートの列数/行数・余白・パディング・画像上限を決める。
- 透過時はプレビュー背景、チェッカー、グリッド、選択表示を描かない。
- 画像出力用の評価器は、実時間の再生速度と切り離す。
- 出力中の編集との整合性は開始時スナップショットで保つ。出力取消や失敗でプロジェクトを変更しない。
- 高解像度や大量フレームの処理は容量・メモリの検証を行い、上限と事前エラーを設ける。

## 7. 3D JSONの契約案

専用識別子・スキーマバージョン、座標系、単位、回転表現、時間単位、階層、エミッター、材質、トラック、素材参照の対応を定義する。編集用データから出力用JSONへ明示的に変換し、スキーマ検証を通す。

未決事項:

- 外部素材を同梱するか、相対参照か、別の配布単位にするか。
- 対象エンジンや専用インポーターとの互換性。
- Bloom等のレンダラー固有設定をどこまで持たせるか。
- JSONからの再インポートを提供するか。

MVP-B必須なのは3D設定JSONの保存・出力。対象エンジンでそのまま動作することや、JSON読込UIの追加は確定していない。

## 8. 往復検証

代表の2D・3Dプロジェクトを用意し、`.vcr`保存→開く→ドメイン値/素材を照合→同時刻で描画を比較する。階層、キー、開始時間、グラデーション、透過、参照素材を含める。生成時刻などのメタ情報を除き、意味の同じデータに戻ることを確認する。自作プリセットと自動保存も同じ整合性検証を使う。

## T04の保存契約（2026-11-07）

保存対象プロジェクトに登録済みの全インポート画像を使用有無にかかわらず同梱する。T04初版のファイルを将来版で開いて再編集できることを保証対象とする。T04のZIPコンテナ版1の物理構造と互換性は[ADR-004](architecture/ADR-004.md)を参照する。

同一ファイルへの上書きを基本とし、非対応環境では明示的にダウンロード方式へ切り替える。ダウンロード開始は保存完了と区別する。通常保存と「保存して開く」の両方で、利用者が保存完了を確認した時点で対象スナップショットを保存済みにする。追加編集の未保存表示を維持し、確認を取り消した場合は現在の編集状態を維持する。利用者確認は完全性検証の結果として表示しない。

未保存で別プロジェクトを開く際は、保存して開く・保存せずに開く・キャンセルを提示する。保存確認後も、次ファイルの検証成功時にだけ置き換える。保存失敗は原因を示し、再試行と別の場所への保存を選べるようにする。保存や読込の失敗・取消では文書、履歴、素材を維持する。

復元候補の日時を表示し、利用者の選択で復元する。実装はT11。復元候補の選択そのものは確定済みで、間隔・世代数・容量はT11で決める。
